  **The ship failed because of me.** `git add` refused with *"Another git process seems to be running"* — a stale 0-byte `.git/index.lock`, created by one of my own `git status` calls and left there because deleting in the mounted folder needed an approval I had not asked for. **`ship.ps1` printed "FAIL: git add failed." and piped git's actual message to `Out-Null`**, so the one sentence that said what was wrong was thrown away and the reader is sent hunting through their own changes.   **Phase 3.2 — the advisory-locked scheduler.** `schedlock.py`. The queue's one-run-per-user rule stops a duplicate *search*; the **scheduler** decides whether a run happens at all, so two instances both seeing the same minute would double every user's Gemini spend before the queue got a say. Postgres: `pg_try_advisory_lock` held on a dedicated connection for the process lifetime — deliberately never returned to the pool, because handing it back drops the lock while the process still believes it holds it. SQLite: granted unconditionally; one file, one writer, and inventing a lock table there would add failure modes to protect against a race that cannot happen. A lock that cannot be taken **fails open** and says so: a safety net that becomes an outage is worse than no safety net.

  **Phase 3.6 — Sentry.** `errors.py`, a thin wrapper rather than an SDK integration (this is stdlib `http.server`; the integrations hook WSGI/ASGI and would see nothing). - 2026-09-15 — **Phase 3 cost guardrails: every Gemini call now goes through one door, and the door counts.** The plan's item 5 asked for "a global daily Gemini spend ceiling, per-user run caps, an admin alert on breach". Before building any of it I audited what already existed, because three plan claims have turned out to be wrong when checked against the code this month.

  **What the audit found, and what it ruled out.** `ingestion/credits.py` does implement monthly caps and a circuit breaker — for the **paid job-source APIs** (Adzuna, TheirStack, Coresignal, Apify, SecretJobs). It has nothing to do with Gemini, and Gemini is where the money goes. The real picture: **ten Gemini call sites** across three modules (`ai_analysis.py` ×4, `app.py` ×5, `apply_engine.py` ×1), each building its own URL and calling `urlopen` itself. **Not one of them counted anything.** Three went through `app._gemini_generate` and so had 429 backoff; **the other seven had none** — which is the mechanism behind the two incidents already recorded on this board as "Gemini 429s degraded prod scoring", where a single un-retried 429 dropped scoring to the keyword heuristic and nothing said so. Also found: `GET /api/jobs` spawns a background thread that makes **one Gemini call per unscored job**, so spend is driven by page loads, not only by searches; and `/api/run-apply` was still spawning a raw thread, so a manual apply bypassed the queue's one-run-per-user rule entirely.

  **The design decision, stated because it is the whole of the change.** A ceiling enforced at ten places is enforced zero times the moment someone adds an eleventh — and the eleventh gets added by copying one of the ten. So: **`gemini.py` is now the only code in this app that names the Gemini host.** It takes the request body each caller already builds and returns the parsed response, so every call site keeps its own prompt and its own parsing; only the metered middle is shared. The retry/backoff moved in with it, so the seven sites that never had it do now. `tests/test_no_unmetered_gemini.py` reads the source and **fails if any file outside `gemini.py` mentions the host** — a crude lint on purpose: a false positive costs one line in an allow-list, a false negative costs a month of unmetered spend.

  **Two limits, because they guard different things.** `gemini.py` holds the **call/token ceiling** (global and per-user, per UTC day); `jobqueue.enqueue` holds the **daily run cap** (`JH_RUNS_SEARCH_PER_DAY`, `JH_RUNS_APPLY_PER_DAY`, default 20). Either alone is weak: a call ceiling still lets one account start fifty searches and spend everyone else's budget before lunch, and a run cap says nothing about one run that scores ten thousand jobs. The run cap lives on `enqueue` rather than on the HTTP route because the **scheduler enqueues too**, and a scheduler-started search costs exactly what a button-started one costs. Counting is on **creations, not completions** — a run that crashed still spent what it spent, and counting completions would let a user retry a crashing run forever.

  **Breach behaviour is the caller's decision**, which is why a spent budget raises a typed `BudgetExceeded` instead of returning a sentinel: job scoring **degrades to the keyword heuristic it already has** (explicitly, in its own `except` clause, so narrowing the bare `except Exception` below it can never turn a spent budget into a 500 for the whole jobs page), while a cover letter **fails loudly** rather than handing the user something the model did not write. A capped search answers **429 with "Resets at midnight UTC"**, never `already_running` — a capped user told work is on its way would wait for a run that is never coming.

  **The ledger is migration 7, `llm_usage`, one row per call**, deliberately **not** foreign-keyed to `users` with cascade: deleting a user would then erase their spend from the day's global total, which is the one number a ceiling must not be able to lose. Tokens come from the response's `usageMetadata`; if that field is ever absent the call is **still counted**, so the guard degrades to call-counting rather than to nothing. Failed calls are counted too, because a loop of failures is exactly what a ceiling should stop. In-process counters re-seed from the ledger, so **a restart does not hand the day a fresh budget** — the process most likely to have just restarted is the one stuck in the runaway loop. A ledger write that fails queues rather than dropping, and a ledger that is entirely unavailable does **not** take Gemini down with it: accounting is not allowed to become an availability dependency.

  **The defaults ship generous, and that is a decision, not an oversight.** No Gemini call in this app had ever been counted, so any "economically meaningful" ceiling would be a number invented from nothing — and one that throttles nine real users is a worse outcome than no ceiling. The defaults (50,000 calls/day global, 1,500/user/day) sit far above anything normal use reaches and well below what a runaway loop does in an hour, which is the catastrophic case. `/api/health` now publishes `llm` (today's spend against today's ceilings) and `smoke.ps1` prints it, **so the real number is readable from outside the box after a week** and the ceiling can be tightened with a Railway variable, no deploy. `JH_LLM_ENFORCE=0` keeps the counting and alerting while dropping the blocking, for the case where a ceiling is set wrongly in production. Breach alerts go to the admin on every channel **and** into `activity_log`, once per day per scope — one notification per blocked call would be the outage's second act.

  **Suite 361 → 395, and every guard was mutation-checked**: neutering the ceiling check, the call counter, the ledger re-seed, the alert dedupe, the run cap, the binding restore, the apply-route queueing, and re-adding an eleventh call site each fail exactly the tests that assert that property, and only those.   **What this does not do.** The counters are per-process, re-synced from the ledger every 30s: with one instance they are exact, with two each undercounts by up to the other's activity within a sync window. That is the same conclusion `ratelimit.py` reached for the same reason, and the same answer applies — Redis, which the project already has a service for, once a second instance exists. - 2026-09-14 — **Phase 3 runtime: the work queue, and the plan's claim design does not work against this codebase.** Migration **6** adds `job_runs` (`user_id, kind, status, payload, attempts, locked_by, locked_at, run_after, …`) with indexes for the two questions the claim asks.   **The plan specified `SELECT … FOR UPDATE SKIP LOCKED`. It cannot be used here, for two independent reasons, both checked rather than assumed:**
  - `dbdriver` opens Postgres connections with **`autocommit=True`** (mirroring `db.get_db()`'s SQLite setup, so `.commit()` at ~189 call sites stays a no-op). The WHERE re-checks the status *inside* the write, which is atomic on both engines - SQLite serialises writers, Postgres locks the row for the statement's duration. Two workers racing means one gets rowcount 1 and the other gets 0 and moves on. Correctness does not depend on the engine; only the amount of retrying does, and with one in-process worker there is none. `SKIP LOCKED` remains a Postgres-only optimisation to reach for if contention ever becomes real.
