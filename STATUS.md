## Changelog (newest first)
- 2026-09-14 — **Phase 2d: the CV files moved into the database, and the volume became a cache.** This was the last thing tying production to one machine's disk. A CV lived only at `UPLOADS_DIR/<user_id>/cv.pdf` on a Railway volume, with the path in `user_profiles.cv_path`. A volume belongs to one service in one environment: it is not in the database dump, it does not follow a rollback, and a redeploy without it starts empty - **the fault that already hit production on 2026-06-23**. Phase 2 could therefore have moved all 10,085 rows to Postgres and still left prod pinned to a disk.

  **Decision (Eran): bytes in the database, not object storage.** 8 CVs, 988 KB total, largest 387 KB - S3/R2 would have bought scale that is not needed for under a megabyte while adding a vendor, a credential to rotate and a new way to be down, before the first paying user exists. Revisit when paid usage is real; it is a smaller rewrite then than a wrong dependency now.

  **How it is built.** Migration **5** adds `user_files` (`user_id`, `kind`, `filename`, `content_type`, `content`, `size`, `sha256`, `uploaded_date`; `UNIQUE(user_id, kind)`, FK cascade). `kind` leaves room for the cover letters and optimised CVs the app already generates without another migration. `ddl_for()` now renders `BLOB` as `BYTEA` on Postgres - **whole-word only**, so a column merely *named* something containing "blob" is not rewritten. New `storage.py` owns the rule that the database is the system of record: `put()` writes the row first and the cache second (a failed cache write is logged, not fatal - the bytes are already durable), and `file_path()` hands callers a path that is readable *right now*, rebuilding the cached file from the database when the volume is cold. That is what let the **~10 `open(cv_path)` call sites in app.py stay as they are** - including the apply engine, which hands a real file to a browser file input. Cache writes go through a temp file plus `os.replace`, so a concurrent reader sees the old complete file or the new one, never a half-written PDF. A pre-2d file on disk with no row is **adopted** into the database on first read, so users the backfill never reached converge on their own.

  **A driver bug found and fixed on the way.** A `bytea` can arrive as a `memoryview` depending on driver version. That is *almost* `bytes` - it slices and compares, so a shallow test passes - but it hashes differently and `str()`s to `<memory at 0x...>`. Left alone it would have turned Phase 2c's value-level migration checksum into a comparison of two pointer addresses: the exact silent corruption that checksum exists to catch. `dbdriver._normalise()` now converts at the row factory.

  **Verified against the real files, not fixtures.** `scripts/import_cv_files.py` imported all **8 production CVs** from the 09-07 backup and read every one back *out of the database* (not the cache) to compare sha256 **and** length against the source: 8/8 matched. Then the verifier itself was tested rather than trusted - **one bit** was flipped in user 3's stored CV, leaving the length identical; `--verify-only` caught it (`3c426ae8a4df in, 5ccf48908d02 out`) and exited **1**, and a re-import repaired it and exited **0**. Suite **257 → 276**, and the new tests were mutation-checked: neutering the database read fails exactly the four tests that assert the Phase 2d property, including the end-to-end one that deletes the uploads directory mid-test and still serves `/api/cv`.

  **One hole closed while in there:** `tests/test_routes.py` re-wired `app.UPLOADS_DIR` after import but not `storage`'s own copy - the same import-order trap that caused the 09-07 admin-role test failure, one module along. Without the fix the route tests would read and write whatever uploads directory the first importer happened to choose.

  **Still to do for production:** run the importer against `jobhunter_prod` as part of the cutover, after the row data is migrated. Until then nothing about production changes - it is still SQLite, and the CV path it has always used still works.
